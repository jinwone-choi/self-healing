# 교육 개념 ↔ 이 프로젝트 대응표

출처: B Track AI Agent 아키텍트 과정 (1~6교시 + 캡스톤)

---

## 한눈에

| 교시 | 개념 | 이 프로젝트에서 | 채택 여부 |
|---|---|---|---|
| 1 | 바이브코딩 (Claude Code로 제작) | 이 파이프라인 자체를 Claude Code로 설계·구현 | ✅ 그대로 |
| 2·3 | RAG (분할·임베딩·검색) | **채택 안 함** — 대신 AST 기반 결정론적 검색 | ⛔ 의도적 배제 |
| 4 | Tool Calling (도구 등록·설명문·실행 분리) | **"결정 vs 실행" 분리 개념만 채택.** 도구 목록은 앱 내부 함수 테이블로만 두고 LLM에 보내지 않음 | 🔶 부분 채택 |
| 5 | MCP (외부 도구 표준 연결) | 사내 배포 시 확장점으로만 | 🔶 보류 |
| 6 | Multi-Agent (역할 분담·위임) | **채택 안 함** — 결정론적 오케스트레이터로 대체 | ⛔ 의도적 배제 |
| 캡스톤 | 요청→판단→Tool→실행결과→업무결과물 | 파이프라인 전체가 이 흐름 | ✅ 그대로 |
| 캡스톤 | 보안 원칙 (사내정보 미입력) | L2/프롬프트 조립 단계의 제약으로 반영 | ✅ 그대로 |

**핵심**: 배운 것을 전부 쓰는 게 목표가 아니라, **어떤 것을 왜 안 썼는지 근거를 대는 것**이
이 과정의 학습 목표(“단일 Agent의 처리 한계를 **근거로** 역할 분담 필요성을 판단”)에 더 가깝다.

## 1교시 — 바이브코딩 ✅

교육에서: 코드를 직접 쓰지 않고 자연어 지시로 제작.
여기서: 설계 문서 → 검증 실험 → 구현 전부 Claude Code로 진행. 실측 스크립트
(`analyze.py` `gaps.py` `capture.py` `llm_ab.py`)도 대화로 만들어 돌렸다.

**개발 도구 AI와 앱 탑재 AI의 분리**도 교육 구성 그대로다.
- 개발 도구 = Claude Code (설계·구현)
- 앱 탑재 = 사내 gemma (테스트 코드 생성). `.env`의 `LLM_BASE_URL` 하나로 교체 가능하게 했다.

---

## 2·3교시 — RAG ⛔ 의도적 배제

교육에서: 문서를 분할·임베딩해 저장하고, 질문과 유사한 조각만 검색해 함께 전달.

여기서 **안 쓴다.** 이유:

| RAG | 이 문제 |
|---|---|
| "무엇이 관련 있는지"를 **유사도로 추정** | 관련 있는 코드가 **정확히 무엇인지 이미 안다** — `coverage.json`의 미커버 라인 번호 + AST |
| 근사 검색 | AST는 정확 검색. 추정할 이유가 없다 |

**RAG의 5단계가 해결하는 문제(무엇을 넣을지 모름)가 여기엔 존재하지 않는다.**
대신 3교시의 **"검색은 왜 실패하고 어떻게 고치는가"** 문제의식은 그대로 살아 있다 —
프롬프트에 무엇을 넣느냐가 성패를 가른다는 점에서. 다만 해법이 임베딩이 아니라 AST일 뿐이다.

> 다만 **rule card 선택**은 구조가 RAG와 같다: 타깃 유형을 키로 관련 카드만 골라
> 프롬프트에 주입한다(`SKILL.md` 3절). 검색기가 임베딩이 아니라 규칙표라는 점만 다르다.

## 4교시 — Tool Calling 🔶 부분 채택

교육에서 배운 도구 등록 딕셔너리는 두 부분으로 나뉜다.

```python
{
    "name": "memo_tool_2",               # ┐
    "description": "새 메모를 저장한다.",  # ├─ LLM에게 보여지는 선언
    "parameters": _TEXT_PARAM,           # ┘
    "function": note_save,               # ── 앱이 실행할 때 쓰는 연결
}
```

**이 프로젝트는 위 3줄을 LLM에 보내지 않고, 아래 1줄만 쓴다.**
즉 도구는 존재하지만 **앱 내부 함수 테이블**일 뿐이고, LLM은 그 존재를 모른다.
호출 순서가 업무 절차로 고정돼 있어 고를 필요가 없기 때문이다.

```python
# 4교시 방식 — LLM이 고른다
resp = llm.chat(messages, tools=[tool1, tool2, tool3])
name, args = resp.tool_calls[0]
registry[name]["function"](**args)

# 이 프로젝트 — 파이썬이 고른다
target = targets.pick_next(coverage, ast_index)   # 계산으로 결정
src    = tools.file_read(target.file, ...)
gaps   = tools.coverage_gap(target.module)
code   = llm.generate(prompt.build(src, gaps))    # LLM은 여기 한 번, 코드만 반환
tools.test_write(path, code)
tools.pytest_run(path)
```

4교시의 핵심 교훈 — **"LLM의 판단"과 "앱의 실행"은 다른 것** — 은 설계 전체의 축으로 남는다.
바꾼 것은 판단의 **범위**다.

| 판단/실행 | 4교시 실습 | 이 프로젝트 |
|---|---|---|
| 어떤 도구를 쓸지 | LLM | 파이썬 (커버리지·AST 계산) |
| 인자를 어떤 JSON으로 | LLM | 해당 없음 |
| **이 함수를 어떻게 테스트할지** | — | **LLM** |
| 실행 | 앱 | 앱 (동일) |

"메모를 찾을까 저장할까"는 LLM이 판단할 가치가 있다. 그러나
**"미커버 62줄인 billing.py를 먼저 할까 3줄인 utils.py를 먼저 할까"는 나눗셈이다.**

### 생성 단계에서도 tool calling 형식을 쓰지 않는다

LLM에게 `{"tests": [...]}` 같은 JSON 스키마를 강제할 수도 있으나 쓰지 않는다.
소형 모델은 JSON 구조를 맞추다 코드 내부의 따옴표·역슬래시·개행에서 자주 깨진다.
마크다운 코드 펜스를 파싱하고 `ast.parse`로 검증하는 쪽이 견고하다.
📌 A/B 실험 20회에서 **펜스 파싱 실패 0건**.

**왜 이렇게 바꿨나 — 4교시 2절 실험이 근거다.** 설명문만 바꿔도 도구 선택이 뒤집힌다는 것은,
뒤집어 말하면 **도구 선택이 프롬프트에 취약하다**는 뜻이다. gemma 계열에서는 그 취약성이
더 크다. 반면 "미커버 라인이 많은 함수부터"는 **계산으로 100% 정확하게 정할 수 있다.**
계산으로 되는 것을 LLM 판단에 맡기지 않는다.

📌 **실측 근거**: A/B 10개 타깃에서 `gpt-4o-mini`조차 통과율이 40~60%였다
(`docs/DECISIONS.md` D3). 이 신뢰도 위에 툴콜 체인을 얹으면 곱해져서 무너진다.

## 5교시 — MCP 🔶 보류 (확장점으로만)

교육에서: 외부 서버를 표준 규격으로 붙여 도구를 늘린다.

지금은 필요 없다 — 필요한 도구(파일·AST·pytest·coverage)가 전부 로컬이다.
**나중에 붙일 자리**는 정해 뒀다:
- 사내 Git/Jira MCP → `refactor_proposals.md`를 이슈로 자동 등록
- 사내 CI MCP → L6 회귀 자가수리를 CI에 연결

MCP의 진짜 교훈("도구 연결을 표준화하면 확장이 싸진다")은 `core/` 모듈 경계 설계에 반영했다.

## 6교시 — Multi-Agent ⛔ 의도적 배제 (가장 중요한 판단)

교육에서: 연구책임자 / 자료조사 / 실험수행 3역할, 도구 목록 자체를 분리, HTTP로 위임.

**첫 설계는 이 구조를 그대로 따랐다가(`총괄/분석/작성`), 사내 도입을 전제로 기각했다.**
6교시 2-3절이 가르친 **"역할 분담의 비용과 이점"** 을 그대로 적용한 결과다.

### 이점 (교육 내용)과 우리 상황

| 6교시가 말한 이점 | 우리 상황 |
|---|---|
| 컨텍스트 한계 회피 | ✅ 유효 — 단, **함수 단위 타깃팅**으로 이미 해결됨 (파일 p90 11.7K → 함수 p90 385토큰) |
| 유지보수 범위 축소 | 🔶 결정론적 모듈 분리로 동일 효과 |
| 기능 확장 용이 | 🔶 동일 |

### 비용 (교육 내용)과 우리 상황

| 6교시가 말한 비용 | 우리 상황 |
|---|---|
| 통신 시간·비용 | ⚠️ 타깃이 수백 개라 위임 오버헤드가 곱해진다 |
| **전달 과정에서 맥락 누락** | ❌ **치명적** — "미커버 라인 127,128,131"을 약한 모델이 지시문에 옮겨 적다 빠뜨리면 그 타깃은 실패한다. 파이썬 코드가 넘기면 100% 정확하다 |

**결론**: 6교시가 가르친 판단 기준을 적용한 결과가 "나누지 않는다"였다.
개념을 안 쓴 게 아니라, **개념을 써서 판단했다.**

> 교육에서 나눈 세 역할은 사라진 게 아니라 **결정론적 모듈로 내려앉았다.**
> 연구책임자 → `core/loop.py` (오케스트레이션·예산·종료판정)
> 자료조사   → `core/targets.py` (AST 분석·우선순위)
> 실험수행   → `core/validate.py` + LLM 1회 호출

### 6교시에서 그대로 가져온 것

**"역할 문구가 아니라 도구 목록 자체를 나눈다"** (3-2절). 이 원칙은 살아 있다.
LLM에게 파일 쓰기 도구를 주고 "tests/ 에만 써라"라고 **부탁하지 않는다.**
`core/validate.py`가 경로를 **강제**하고, SHA-256으로 검증한다
(`SKILL.md` 2절 "프롬프트로 부탁할 것 vs 코드로 강제할 것").

## 캡스톤 요구사항 대응 ✅

교육이 요구한 흐름:

```
사용자 요청 → LLM이 필요한 행동 판단 → Tool 실행 → 실제 데이터/실행 결과 → 업무 결과물
```

이 프로젝트:

```
저장소 경로 → (커버리지·AST로 타깃 판단) → LLM이 테스트 코드 생성 →
pytest 실제 실행 → 커버리지 측정값 → tests/ + 80% 게이트 + 리포트
```

캡스톤 4-1의 세 질문:

| 질문 | 답 |
|---|---|
| 어떤 입력을 받는가 | 저장소 경로 (+ 목표 커버리지, 예산) |
| 어떤 Tool을 실제로 쓰는가 | 파일 읽기/쓰기, AST, pytest, coverage, git |
| 어떤 업무 결과물이 나오는가 | 테스트 스위트 + 커버리지 리포트 + 리팩터링 제안서 + 발견한 결함 목록 |

**"정량 결과는 실제 코드 실행 결과를 사용하세요"** (6교시 4-2)는 이 프로젝트의 절대 규칙으로
격상돼 있다 — 보고하는 커버리지는 반드시 `pytest --cov` 종료 코드로만 판정하고,
LLM이 추정한 값은 쓰지 않는다.

### 보안 원칙 (캡스톤 3절) ✅

- 검증 실험은 **공개 OSS**(click / boltons / requests)로만 수행했다
- 사내 repo 연결 시: 코드가 사내 gemma로만 가고 외부 API로 나가지 않도록 `LLM_BASE_URL` 고정
- "대화가 깊어지며 민감정보가 섞인다"는 경고는 이 파이프라인에서 특히 중요하다 —
  **소스 코드 자체를 프롬프트에 넣기 때문**이다. 프롬프트 조립부(`core/prompt.py`)가
  외부 엔드포인트로 갈 때는 거부하도록 만드는 것이 안전하다

## 학습목표 대비 자기점검

| 교육 학습목표 | 이 프로젝트에서의 답 |
|---|---|
| Claude Code로 코드를 직접 쓰지 않고 제작·수정 | ✅ 설계·실험·구현 전부 |
| RAG 5단계를 설명하고 각 단계를 진단·개선 | 🔶 배제했으나 **왜 배제했는지 근거 제시** |
| AI에 도구를 제공하고 **도구 선택의 판단 근거를 설명** | ✅ "설명문 취약성 + 실측 통과율 40~60%" 근거로 **툴콜을 쓰지 않기로 판단** |
| 단일 Agent의 한계를 **근거로** 역할 분담을 판단 | ✅ 6교시 비용·이점 기준을 적용해 **나누지 않기로 판단** |

마지막 두 줄이 이 프로젝트의 발표 포인트다.
"멀티 Agent를 만들었다"보다 **"만들지 않기로 한 근거가 측정값으로 있다"** 가 더 강한 결과다.
