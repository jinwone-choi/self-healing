# Self-Healing 아키텍처

목표: **커버리지 80% 하드 게이트 통과** (사내 규칙, 협상 대상 아님)
수단: 실패를 감지하고 **사람 개입 없이 스스로 복구하는 폐루프**를 6개 층에 깐다
제약: business code는 기본적으로 건드리지 않는다 (예외는 L4 — 명시적 사람 승인 게이트)

---

## 0. self-healing을 무엇으로 정의하는가

멀티 Agent 툴콜이 self-healing인 게 아니다. **실패 신호 → 원인 분류 → 조치 → 재검증**의
루프가 사람 없이 닫히면 self-healing이다. 그 루프는 결정론적 코드로 짜는 게 더 튼튼하다.
LLM은 루프 안에서 "코드를 쓰는" 한 스텝만 맡는다.

```
        ┌──────────────────────────────────────────┐
        │  감지 → 분류 → 조치 → 재검증 → (미해결이면 상위 층으로)  │
        └──────────────────────────────────────────┘

L0  생성 자가수리    파싱 실패 / import 오류        → 즉시 재생성
L1  테스트 자가수리   pytest 실패                   → 오류 유형별 수리 (최대 2회)
L2  환경 자가수리     venv / pip 설치 실패           → 결정론적 레시피 → LLM 폴백 → 부분 진행
L3  전략 자가수리     커버리지 정체                  → 에스컬레이션 사다리 (S1~S5)
L4  게이트 자가수리   사다리 소진 & 80% 미달         → 리팩터 제안 → 사람 승인 → 적용 → 검증 → 롤백
L5  스위트 자가수리   전체 실행 시 간섭 / flaky      → 이분 탐색 격리 → 수정 or 제거
L6  회귀 자가수리     (CI 상시) 소스 변경으로 깨짐    → 3분류 → 갱신 / 수정 / 알림
```

각 층은 **자기 층에서 못 고치면 위로 올린다.** 아래 층에서 조용히 포기하지 않는다.
이게 80% 게이트를 실제로 넘기는 구조다 — 기존 계획은 L0·L1만 있었고, 정체하면 그냥 멈췄다.

---

## L0 — 생성 자가수리 (LLM 호출 0회)

모델 출력이 코드로 성립하지 않는 경우. **LLM을 다시 부르기 전에 코드로 고친다.**

| 증상 | 조치 |
|---|---|
| 코드 펜스 밖에 설명문이 섞임 | 펜스만 추출. 펜스가 없으면 `def test_` 부터 끝까지 슬라이스 |
| `ast.parse` 실패 | 마지막 불완전 함수 절단 후 재파싱. 그래도 실패 시 재생성 |
| import 경로 오류 | 프롬프트에 박아준 정답 import로 **문자열 치환**. 모델에 다시 묻지 않는다 |
| `test_` 접두사 누락 | 함수명 자동 교정 |
| 중복 함수명 | 접미사 자동 부여 |

소형 모델 실패의 30~40%가 여기다. **LLM 재호출 없이 해결되므로 가장 싸고 효과가 크다.**
L0에서 고친 건 `healing_log` 에 기록하되 재시도 카운트를 소모하지 않는다.

---

## L1 — 테스트 자가수리 (LLM 최대 2회)

pytest 실패를 **유형별로 다르게** 처리한다. 전부 LLM에 던지지 않는다.

| 실패 유형 | 조치 | LLM 호출 |
|---|---|---|
| `ModuleNotFoundError` (테스트 대상) | `sys.path`/`conftest.py` 자동 보강 | 없음 |
| `ModuleNotFoundError` (서드파티) | L2로 승격 (설치 누락) | 없음 |
| `fixture not found` | 표준 fixture(`tmp_path`, `monkeypatch`)면 시그니처 자동 주입 | 없음 |
| `DID NOT RAISE` | `pytest.raises` → 반환값 단언으로 자동 전환 시도 | 없음 |
| `AssertionError` (characterize 모드) | 실제값 캡처해 기대값 **자동 갱신** | 없음 |
| `AssertionError` (strict 모드) | 실제값·기대값 함께 넣어 재생성 | 1회 |
| `AttributeError` (패치 위치 오류) | `patching.md` 카드 주입해 재생성 | 1회 |
| `Timeout` | 폐기 + 해당 타깃 블랙리스트 | 없음 |
| 무결성 위반 | 즉시 폐기 + 전체 중단 경보 | 없음 |

**characterize 모드에서 `AssertionError`가 LLM 호출 없이 해결된다**는 점이 중요하다.
소형 모델 실패 1위 유형이 결정론적으로 사라진다. 이게 characterize를 기본값으로 두는 진짜 이유다.

2회 실패 시 폐기하고 다음 타깃으로. **단, 폐기된 타깃은 큐에서 지우지 않고 L3의 S2 단계에서
더 잘게 쪼개 재도전한다.** 영구 포기는 L4에서만 한다.

## L2 — 환경 자가수리

> 지난 계획에서는 "설치 실패 시 즉시 중단"으로 잡았는데, 그러면 self-healing이 아니다.
> **결정론적 레시피 우선, LLM은 마지막, 그래도 안 되면 부분 진행**으로 바꾼다.

### 2-1. pip 실패 레시피 (결정론적, LLM 0회)

pip stderr를 정규식으로 분류해 정해진 조치를 순서대로 시도한다.

| 증상 | 조치 |
|---|---|
| `requirements.txt` 없음 | `pyproject.toml` → `setup.py` → `poetry.lock` → `Pipfile` 순 탐색 |
| `No matching distribution` + 버전 제약 | 사용 가능한 다른 파이썬(3.9/3.10/3.11/3.12)으로 venv 재생성 |
| C 확장 빌드 실패 | `--only-binary=:all:` 재시도 |
| 인덱스/네트워크 오류 | 사내 미러 인덱스로 재시도 (`PIP_INDEX_URL`) |
| 의존성 충돌 | `--no-deps` 로 개별 설치 후 import 가능 여부로 판정 |
| 특정 패키지 1개만 실패 | **그 패키지만 빼고 계속.** 해당 패키지를 import하는 모듈은 타깃에서 제외 |

### 2-2. LLM 폴백 (1회, 강한 제약)

레시피가 다 실패하면 pip 로그 **마지막 40줄**만 주고 다음 명령 **1개**를 받는다.
받은 명령은 **allowlist 검증을 통과해야만 실행한다** (`pip install` + 허용된 플래그만).
임의 셸 명령은 실행하지 않는다.

### 2-3. 부분 진행 (graceful degradation)

전부 실패해도 멈추지 않는다. **import 가능한 모듈만 타깃 집합으로 삼아 진행**하고,
제외된 모듈과 사유를 리포트에 남긴다. 커버리지 분모도 그에 맞춰 보고한다
(전체 기준 / 실행 가능 범위 기준 **두 숫자를 모두** 낸다. 하나만 내면 숫자가 사람을 속인다).

## L3 — 전략 자가수리 (에스컬레이션 사다리) ★ 80% 달성의 핵심

정체를 **종료 조건이 아니라 승급 조건**으로 바꾼다. 기존 계획의 가장 큰 결함이 여기였다.

| 단계 | 진입 조건 | 조치 | 비용 |
|---|---|---|---|
| **S0** 기본 | 시작 | 순수 함수 우선 · `candidates=3` · characterize · 카드 1장 | 기준 |
| **S1** 후보 증폭 | 10타깃 연속 수락 0건 | `candidates` 3→6, `temperature` 0.8, 카드 2장 | LLM 2배 |
| **S2** 타깃 재분해 | **정체와 무관하게 상시** (아래 참조) | 함수 단위 → **미커버 라인 그룹 단위**. "이 함수를 테스트하라"가 아니라 **"127~131번 라인을 지나게 하는 입력을 써라"** + 해당 라인 소스 제시 | 프롬프트 재조립 |
| **S3** 의존 대상 개방 | 순수 함수 큐 소진 | 버킷 A의 I/O 의존 타깃 진입. `patching` / `filesystem` / `time-and-random` 카드 | 성공률 하락 감수 |
| **S4** 분모 정리 | 잔여 공백의 30% 이상이 D버킷 | `.coveragerc` 제안 → **사람 승인 필수**. ⚠️ 실측 기대 효과 약 **0.8%p**뿐 | LLM 0회 |
| **S5** 게이트 승급 | 위 전부 소진 & 80% 미달 | L4로 | 사람 개입 |

### S2는 에스컬레이션 단계가 아니라 상시 모드다 (실측으로 수정됨)

당초 S2를 "정체 시 꺼내는 비상수단"으로 설계했으나, click 실측 결과 **틀렸다.**

| 커버리지 | 완전 미커버(함수 단위가 맞음) | 부분 미커버(라인그룹이 맞음) |
|---|---|---|
| 26.7% | 99% | 1% |
| 54.9% | 69% | 31% |
| 87.1% | 52% | **48%** |

**80% 게이트에 가까워질수록 미커버의 절반이 부분 미커버**가 된다. 즉 게이트 근처에서는
라인그룹 타깃팅이 주력이다. 따라서 S2는 정체 트리거가 아니라 **타깃마다 판정**한다.

```
함수 body에 실행된 문장이 하나도 없음  → 함수 단위 프롬프트
일부만 실행됨                        → 라인그룹 프롬프트
```

미커버 구간은 **1~3줄짜리 파편이 85~90%**이므로(덩어리가 아니다), 한 함수에 구간이 여럿이면
구간별로 LLM을 호출하지 말고 **한 프롬프트에 묶어서** 준다. 근거: `docs/DECISIONS.md` D2.

### S4에 대한 경고

분모를 줄여 80%를 넘기는 건 **정당한 경우에만** 허용된다 (자동 생성 코드, `__main__`,
`TYPE_CHECKING`, C 확장). 그래서 사람 승인을 강제하고, 리포트에는 **제외 전/후 커버리지를
둘 다** 적는다. 이 두 숫자를 나란히 두지 않으면 게이트 통과가 숫자놀음이 된다.

## L4 — 게이트 자가수리 (리팩터 승인 루프)

사다리를 다 올라도 80%에 못 미치면, 남은 길은 하나다: **C버킷 리팩터링.**
여기는 business code를 건드리므로 **사람 승인 게이트**를 둔다. 자동으로 넘어가지 않는다.

```
1. refactor_proposals.md 생성
   변경 라인 수 대비 예상 커버리지 획득량 순 정렬
   각 제안: 수술 종류(seam 1~5) / diff / 호출부 영향 / 예상 획득 %p

2. ⏸ 사람 승인  ← 여기서 멈춘다. 승인 없이 진행하지 않는다

3. 승인분만 별도 브랜치에 적용
   안전망: 지금까지 생성한 characterization test 전체

4. 자동 검증
   ✅ 기존 테스트 100% 통과  (동작 불변 증명)
   ✅ 커버리지 하락 없음
   → 통과하면 유지, 하나라도 실패하면 git 자동 롤백

5. 재실행 → 게이트 재판정
```

**4번이 이 전체 설계가 말이 되는 이유다.** characterization test가 "리팩터링 전후 동작이
같다"를 자동으로 증명하므로, 리팩터링 결과도 self-healing 루프 안에서 검증·롤백된다.
말씀하신 "테스트가 있으니 나중에 마음대로 수정할 수 있다"가 바로 여기서 실현된다.

승인이 거절되거나 그래도 80% 미달이면 → **exit 1 + 귀속 리포트**.
게이트를 통과한 척하지 않는다. 남은 공백을 `순수로직/IO의존/프레임워크/데드코드/리팩터필요`로
라인 단위 귀속해 보고한다.

## L5 — 스위트 자가수리

개별 격리 실행에서는 통과했는데 전체 스위트로 돌리면 깨지는 경우. 반드시 생긴다.

```
1. 전체 실행 (기본 순서 + 랜덤 순서 2회)
2. 실패 발생 → 이분 탐색으로 간섭 쌍 격리   ← pytest -p no:randomly 로 재현성 확보
3. 원인 분류
     전역 상태 오염   → autouse fixture 자동 주입 (class-and-state 카드)
     tmp 파일 잔존    → tmp_path 로 전환
     import 순서 의존 → 해당 테스트 재생성
     원인 불명        → 제거 (커버리지 손실 감수)
4. 재실행 → 2회 연속 동일 결과일 때만 확정
```

이 층 때문에 **"게이트 통과"는 전체 스위트 완주로만 판정한다.** 누적 `.coverage` 숫자만으로
선언하지 않는다.

## L6 — 회귀 자가수리 (CI 상시 모드)

여기가 장기 가치다. 한 번 80%를 만들고 끝이 아니라, 소스가 바뀌어도 스위트가 스스로 따라간다.

```
소스 변경으로 테스트 실패
  → git diff 로 변경된 함수 식별
  → 3분류
      (a) 의도된 동작 변경   : characterization 기대값 갱신 제안 → 사람 승인 → 반영
      (b) 테스트의 취약성    : 테스트 자동 수정 (L1 재사용)
      (c) 진짜 회귀          : 수정하지 않는다. 알림 + 실패 유지  ← 테스트의 존재 이유
  → 커버리지가 80% 아래로 떨어지면 신규/변경 함수 대상 생성 루프 자동 기동
```

**(c)를 절대 자동 수리하지 않는 것이 핵심이다.** 깨진 테스트를 자동으로 고치는 시스템은
회귀 검출 능력을 스스로 0으로 만든다. (a)와 (c)의 구분 기준은 "변경이 의도적인가"이고,
그건 기계가 판정할 수 없으므로 **사람 승인**으로 넘긴다.

## 학습 — 실행 간 self-healing

`reports/healing_log.json` 에 **어떤 조치가 어떤 효과를 냈는지** 누적한다.

```json
{
  "repo": "payments-core",
  "best_config": {"mode": "characterize", "candidates": 5, "cards": ["patching"]},
  "escalation_reached": "S2",
  "recipes_that_worked": {"pip": ["--only-binary=:all:"], "python": "3.10"},
  "target_blacklist": ["src/hw/serial.py::open_port"],
  "l0_fix_rate": 0.34,
  "l1_fix_rate_by_kind": {"AttributeError": 0.71, "DID NOT RAISE": 0.88}
}
```

다음 실행은 S0부터 더듬지 않고 **직전에 통했던 설정에서 시작**한다(warm start).
같은 repo를 반복해서 도는 사내 환경에서는 이 누적이 가장 큰 속도 개선이 된다.

## 게이트 판정과 정직성 세트

`pytest --cov --cov-fail-under=80` 종료 코드 0 = 통과. **이것만이 통과 판정이다.**

단, 통과를 보고할 때 다음 4개를 **항상 함께** 낸다. 80%라는 숫자 하나만 보고하면
리뷰어가 검증할 방법이 없다.

| 항목 | 왜 |
|---|---|
| characterize 테스트 비율 | 회귀 방지용인지 정답 검증용인지 구분 |
| 분모 제외 라인 수 + 제외 전/후 커버리지 | S4가 남용되지 않았음을 증명 |
| mutation score (상위 모듈 표본) | 커버리지가 거짓말하는지 아는 유일한 지표 |
| 도달한 에스컬레이션 단계 | S0에서 끝났으면 여유, S5까지 갔으면 이 repo는 관리 필요 |
