# 설계 의사결정 기록 (측정 근거 포함)

모든 결정은 **실측**으로 검증했다. 측정 대상: `click` (4,877 stmt), `boltons`, `requests`
실측 환경: Python 3.14.4 / pytest 9.1.1 / coverage 7.16.1 / 모델 `gpt-4o-mini`
재현 스크립트: `analyze.py`(구조), `gaps.py`(공백분포), `capture.py`(치환), `llm_ab.py`(A/B)

> **모델에 대한 단서**: A/B는 `gpt-4o-mini`로 측정했다. gemma의 **절대 수치**는 이보다 낮을
> 것이다. 다만 여기서 검증한 것은 대부분 **모델 무관한 메커니즘**(커버리지 회계, 치환, 패치
> 위치)이고, 모드 비교는 **상대 순위**를 본 것이다. 약한 모델일수록 격차는 벌어지는 방향이다.

## D1. 타깃 입도 — 파일 단위가 아니라 **함수 단위**

**결정: 함수 단위. 파일 단위는 기각.**

| 지표 | boltons | click | requests |
|---|---|---|---|
| 파일 토큰 p50 | 3,757 | 4,763 | 1,141 |
| 파일 토큰 p90 | 11,801 | 11,710 | 9,015 |
| 파일 토큰 최대 | 14,834 | **37,302** | 10,365 |
| **4K 초과 파일 비율** | **46.7%** | **56.2%** | 26.3% |
| 함수 토큰 p50 | 62 | 84 | 96 |
| 함수 토큰 p90 | 281 | 385 | 368 |
| 함수 토큰 최대 | 2,390 | 1,769 | 1,242 |
| **2K 초과 함수 비율** | **0.1%** | **0.0%** | **0.0%** |

파일 단위는 절반 가까이가 4K 컨텍스트에 **애초에 안 들어간다**. 함수 단위는 사실상 전부 들어간다
(p90 기준 파일 대비 **30배** 작음). 함수의 84~90%가 30줄 이하로 크기도 균일하다.

부수 발견: 60줄 초과 함수는 개수로는 2.8~4.5%뿐이지만 **전체 라인의 19~23%를 차지**한다.
`docs/TESTABILITY.md` C-3(Extract function) 제안의 대상이 이 소수 집단으로 정량화된다.

## D2. 입도는 고정이 아니라 **커버리지 수준에 따라 동적 전환** ★

**결정: 타깃마다 판정. 프로젝트 단위로 정하지 않는다.**

같은 저장소(click)를 세 커버리지 지점에서 측정했다.

| 커버리지 | 미커버 라인 중 **완전 미커버 함수**(한 번도 호출 안 됨) | **부분 미커버 함수**(일부 분기만) |
|---|---|---|
| 26.7% (테스트 없음) | **99%** | 1% |
| 54.9% | 69% | 31% |
| 87.1% | **52%** | **48%** |

→ **초반에는 "이 함수의 테스트를 써라"(함수 단위)가 맞고, 80% 게이트에 가까워질수록
"이 라인들을 지나게 하라"(라인그룹 단위)가 절반을 차지한다.**

즉 라인그룹 타깃팅은 정체했을 때 꺼내는 비상수단(기존 계획의 S2)이 아니라,
**게이트 근처의 주력 모드**다. 판정 규칙:

```
함수 body에 실행된 문장이 하나도 없음   → 완전 미커버 → 함수 단위 프롬프트
일부만 실행됨                          → 부분 미커버 → 라인그룹 프롬프트
```

**측정 주의**: "완전 미커버" 판정은 `def`/데코레이터 줄을 제외한 **body 범위**에서
`executed_lines`가 비었는지로 해야 한다. 이 두 가지를 틀려서 초기 측정이 두 번 잘못 나왔다.
- `def`/데코레이터 줄은 import 시점에 실행되므로 포함하면 전부 "부분"으로 오분류된다.
- body 첫 줄이 docstring이면 측정 대상 문장이 아니라서 `missing`에 없다.

### 라인그룹의 크기

| 커버리지 | 연속 미커버 구간 수 | 구간 길이 p50 | p90 | 1~3줄 구간 비율 |
|---|---|---|---|---|
| 26.7% | 1,584 | 2 | 4 | 85% |
| 54.9% | 1,018 | 1 | 4 | 89% |
| 87.1% | 327 | 1 | 3 | **90%** |

미커버는 **덩어리가 아니라 1~3줄짜리 파편**이다. 따라서 라인그룹 프롬프트는
"이 3줄을 지나게 하는 입력을 만들어라" 형태여야 하고, 한 함수에 구간이 여럿이면
**구간별로 호출하지 말고 한 프롬프트에 묶어서** 준다(구간 수 / 함수 = 1.8~3.2).

## D3. 생성 모드 — **characterize 기본값** (실측 A/B)

**결정: characterize 기본, strict는 옵션.**

click의 완전 미커버 함수 10개, 동일 타깃·동일 온도(0.2)·후보 1개·수리 0회:

| 모드 | 통과율 | 미커버 라인 획득률 |
|---|---|---|
| strict (모델이 기대값 작성) | 4/10 = **40%** | 38/113줄 = **34%** |
| characterize (하네스가 기대값 주입) | 6/10 = **60%** | 59/113줄 = **52%** |

획득률 기준 **1.5배**. 실패 유형 분포도 다르다.

```
strict       : gate:no_assert 3,  attribute_error 2,  assertion_error 1
characterize : gate:no_assert 1,  attribute_error 1,  type_error 1,  did_not_raise 1
```

strict에서만 나온 `assertion_error`(기대값 오답)가 characterize에서는 **구조적으로 사라진다**.
이것이 약한 모델에서 격차가 더 벌어질 것으로 보는 근거다.

예상과 달랐던 점: **최대 실패 원인이 `no_assert`(단언 없는 테스트)였다.** 데코레이터 함수에서
모델이 "호출만 하고 끝나는" 테스트를 쓴다. 정적 게이트가 이를 잡아냈다(설계대로 동작).
→ 게이트 위반은 폐기가 아니라 **"단언을 반드시 넣어라"를 붙여 1회 재생성**하도록 한다.

## D4. `__CAPTURE__` 치환 메커니즘 — 센티널 방식 (구현·검증 완료)

**결정: `__eq__`가 항상 True를 반환하며 상대 피연산자를 기록하는 센티널 주입.**
AST 평가나 로컬 변수 재현이 필요 없다. 구현: `capture.py`.

검증 결과 (`int / str / list / dict / float / 커스텀객체`):

```
assert num(21)   == __CAPTURE__   →  == 42          ✅
assert text("a") == __CAPTURE__   →  == '<a>'       ✅
assert lst(1)    == __CAPTURE__   →  == [1, 2]      ✅
assert dct(7)    == __CAPTURE__   →  == {'k': 7}    ✅
assert num(0.1)  == __CAPTURE__   →  == 0.2         ✅
assert obj(3)    == __CAPTURE__   →  미채움         ✅ (repr 복원 불가를 자동 검출)
```

**필수 부품: repr 라운드트립 검증.** 채우기 전에 `repr(eval(rep)) == rep` 를 확인한다.
`<pkg.v.Obj object at 0x...>` 같은 값은 채우면 문법 오류가 되므로 **해당 테스트 함수를 폐기**한다.

구현 주의: 센티널의 프레임 필터를 `co_filename` 비교로 하면 Windows 경로 표기 차이로
전부 실패한다. `sys._getframe(1).f_lineno`를 직접 쓴다.

부수 확인: A/B 10회 중 치환 실패는 **실패한 테스트에서만** 발생했고(3/2/1건),
통과한 6건은 전부 0건이었다. 즉 치환 메커니즘이 독립적인 실패 원인이 되지 않는다.

## D5. 커버리지 회계 — **후보는 별도 데이터파일, 수락 시에만 combine** ★

**결정: 후보마다 `COVERAGE_FILE`을 분리하고, 통과+기여>0 일 때만 누적본에 combine.**

이걸 검증하다 **설계 결함 2개**를 찾았다.

### 결함 1 — 실패한 테스트도 커버리지를 기록한다

```
기준선(test_a만)           : 44%
실패하는 test_d 실행 후     : 56%   ← 테스트는 FAILED인데 커버리지는 올라감
```

누적본에 바로 `--cov-append` 하면 **폐기한 후보의 라인이 남아 커버리지가 부풀려진다.**
80%를 넘겼다는 보고가 거짓이 된다. 기존 계획(누적본에 append 후 롤백)은 여기서 깨진다.

### 결함 2 — `.coverage.<접미사>` 이름의 백업은 자동 병합되어 사라진다

```
cp .coverage .coverage.snapshot
(다음 --cov-append 실행)
→ .coverage.snapshot 이 parallel 데이터로 인식되어 병합·삭제됨
```

백업은 반드시 `.coverage.*` **네임스페이스 밖**(예: `bak/safe.bin`)에 둔다.

### 검증된 올바른 절차

```
1) 후보 실행:  COVERAGE_FILE=cand/c1.bin  pytest <후보파일만>
2) 실패 → 파일만 삭제. 누적본 무손상 (44% → 44% 확인)
3) 통과 → cand/c1.bin 을 .coverage.cand 로 복사 후 coverage combine --append
4) 결과 대조
     격리+combine 누적 : 56%
     전체 동시 실행(정답): 56%   ✅ 정확히 일치
```

## D6. 우선순위 — ROI 정렬은 유효

click(87.1%) 기준: **미커버 라인의 50%를 덮는 데 상위 25개 함수(전체의 13%)면 충분**하다.
롱테일이 확실하므로 ROI 정렬은 실효가 있다. 다만 나머지 50%는 87%의 함수에 흩어져 있어,
**80% 게이트의 마지막 구간이 가장 비싸다**는 뜻이기도 하다.

## D7. `.coveragerc` 사전 정리 효과 — **기대치 하향**

앞선 계획에서 "LLM 없이 5~15%p 오른다"고 썼는데, 실측은 그보다 작다.

```
click 미커버 631줄 중 D버킷(제외 가능) 후보 = 40줄 = 6%
  import 15 / pass 12 / signature 9 / bare_reraise 4
```

**커버리지로는 약 0.8%p 상승**에 그친다. 여전히 공짜이므로 하지만,
**S4(분모 정리)로 게이트를 넘기려는 기대는 버려야 한다.** 이전 추정은 과장이었다.

## D8. monkeypatch 위치 — use-site (재현 검증)

```
monkeypatch.setattr(notify, "send_mail", fake)      → PASSED  ✅
monkeypatch.setattr("pkg.mailer.send_mail", fake)   → FAILED (실제 함수가 실행됨)
```

`rules/patching.md` 카드의 주장이 맞다. A/B에서도 `attribute_error`가 두 모드 모두에서
상위 실패 유형이었으므로, 이 카드는 **기본 주입 대상**으로 승격한다.

## D9. 정적 분석 기반 버킷 분류의 한계 — **사전 확정하지 않는다**

AST 휴리스틱으로는 `pure_fn`이 94~95%로 나온다(3개 저장소 모두). 이는 명백한 **과대추정**이다.
`self.session.get()`, `from x import y` 후 `y()` 같은 형태를 못 잡기 때문이다.

**결정: 버킷 분류는 사전 필터가 아니라 _사전 정렬 힌트_로만 쓴다.**
실제 판정은 "돌려보면 안다". 실행 결과를 `healing_log`에 누적해
**사후 학습된 분류**를 다음 실행의 우선순위에 반영한다.

---

## D10. L0 결정론적 교정 — 유지하되 기대치는 모델 의존

`gpt-4o-mini`에서는 L0 교정이 **0건 발동**했다(항상 코드펜스 + 정확한 import 출력).
gemma에서는 다를 것이므로 유지한다. **비용이 0이므로 유지 판단에 손해가 없다.**
단 "소형 모델 실패의 30~40%가 L0"라는 앞선 추정은 **미검증 가설**이며,
gemma 연결 후 `healing_log.l0_fix_rate`로 실측해야 한다.
